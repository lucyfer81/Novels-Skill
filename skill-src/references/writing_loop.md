# 写作循环：指令行为定义

## 目标项目锁定协议

执行本文件任何指令前，先按 SKILL.md「核心协议：目标项目锁定与隔离红线」确定 `{project_dir}`（唯一权威定义，此处不重复）。参数为 `new` 时转入 `references/init_flow.md` 初始化流程。

## 槽位解析（每次写作/审阅类指令的先决步骤）

本文件使用两个抽象槽位，实际文件名由题材包声明（见 SKILL.md「题材包协议」）：

- `{core_doc}` = 核心设定文档（作者持有的终局类文档）
- `{signal_doc}` = 投放物地图（投放物的登记与状态跟踪）

🔴 执行任何指令前：读取 `{project_dir}/meta/project_info.md` 确认 genre → 读取 `references/genres/{genre}/manifest.md` 解析槽位 → 需要题材行为（预检/投放/自查/封存核对/审阅维度）时 🔴 完整读取 `references/genres/{genre}/hooks.md`。只加载当前题材的题材包。

## `/write [项目名|new]` — 推进剧情

### 执行前准备（必须完成，按顺序）

**第0步：确定目标项目与当前段落编号（每次 /write 必须先做这一步）**

1. 确认已锁定 `{project_dir}`（若指令为 `/write new` 则转入初始化流程）；完成上方「槽位解析」
2. 检查 `{project_dir}/drafts/chXX_draft.md` 是否存在：
- 文件不存在 → 当前为**第1段**，本次 /write 将创建文件
- 文件存在，内容只有1段（约900字）→ 当前为**第2段**
- 文件存在，内容有2段（约1800字）→ 当前为**第3段（最终段）**

判断完成后，在内心确认："本次我将写第X/3段"，并以此决定本次输出的结束行为（暂停 or 封存协议）。

```
0. 读取 {project_dir}/meta/project_info.md，获取 genre 和 language 字段
    - genre → 按上方「槽位解析」加载题材包 manifest 与 hooks.md
    - language: zh / en → 确认本次 /write 输出语言
    - 🔴 从本步骤起执行「分层记忆」读取纪律（与 auto_agents.md 3.2 自读清单同构）：
      {core_doc} 先读骨架节（manifest `core_skeleton` 字段），再读 outline 本章「核心依据」
      字段指向的分节；任一缺省 → 全文读取；揭示/终局章一律全文通读
    - 据此读取 {project_dir}/meta/{core_doc}（核心设定文档：你始终持有它——既提醒自己
      不能泄露的终局信息，也对齐当前章节的目标状态）

1. 读取 {project_dir}/meta/style_guide.md（仅加载"绝对禁止"和"样板句式"两节）

2. 读取 {project_dir}/meta/characters.md 本章出场角色条目
   ⚠️ 首次出场角色只加载以下字段：
   - 出场前读者已知信息
   - 出场引入方式
   - 身份（仅职业/社会角色）
   完整档案（性格及 manifest「sanitize_fields」所列的题材终局性字段）须在该角色二次出场后才解锁。
   ⚠️ 首次/二次出场的判定一律以角色条目中的「出场记录」字段为准（不由记忆判断）。

3. 读取 {project_dir}/meta/{signal_doc}：「总索引」节全量 + outline 本章计划标注编号
   （应投 / 将触碰 / 结构操作引用）的全条目；写作中触及索引内其他活跃投放物时，先读该条目
   全文再落笔；文件无「总索引」节 → 全文读取

4. 若 {project_dir}/drafts/chXX_draft.md 存在：读取全文（衔接 + 确认段落数）；否则读取上一章 chXX.md 最后 500 字

5. 读取 {project_dir}/meta/session_log.md 最近 2 章条目（核心事件、角色变化、故事内时间/地点、信息增量、下章切入点）——这是跨章衔接与一致性核对的基准；即使第4步已读本章草稿也必须读取

6. 读取 {project_dir}/meta/outline.md 中本章的计划节点（本章目标、应投投放物、结构操作、应揭秘密、章末钩子、核心依据等——字段名以题材包 outline 模板为准）

7. 读取 {project_dir}/meta/continuity.md（场景登记 + 事实断言——写作前知晓，防场景复写与事实矛盾；旧项目无此文件则跳过）
```

### 写作前行为预检

按题材包 `hooks.md` 的「write_preflight」执行（高风险场景前的角色行为逻辑自查）。

### 写作规范

**字数与节奏**：每章目标 zh 约 2700 字 / en 约 1800 词，分三段推进，每段 zh 约 900 字 / en 约 600 词。

⚠️ 字数硬约束（每段写完后必须自查）：
- 每段目标范围：zh 850–950 字 / en 550–650 词（按 language 字段选择标准）
- 低于下限：禁止输出 PAUSE 标记，必须补写至达标
- 超过上限：检查是否有可拆入下一段的内容，若无则允许保留
- 自查方式：输出正文后，在内心估算段落字数/词数，不达标则继续写，不得以"段落自然结束"为由提前停止

**重要：每次 `/write` 只生成一段。** 模型不自行连续生成三段——暂停由对话结构保证，而非模型自我中断。

**投放原则（交互模式同样遵守）**：按题材包 `hooks.md` 的「signal_budget」执行（每章投放预算、设计纪律、登记义务；投放以 outline.md 本章计划为准，偏离必须显式说明，禁止无声遗漏）。登记编号与结构术语只用于 meta 文档与写作后记，正文与对白中一律不得出现（见 signal_budget 的"编号不入正文"规则）。

**第一段（约900字）**：开场，推进到一个"信息悬停点"后结束本次输出，将本段正文 **append 写入** `{project_dir}/drafts/chXX_draft.md`，然后给出三分选择，等待用户回应。
**第二段（约900字）**：根据用户在第一段后的选择推进，到"张力转折点"后结束本次输出，将本段正文 **append 写入** 同一 `{project_dir}/drafts/chXX_draft.md`，给出三分选择，等待用户回应。
**第三段（约900字）**：收拢本章，以"悬而未决的尾音"结束——不解答，提出下一章的核心问题。将本段正文 **append 写入** 同一 `{project_dir}/drafts/chXX_draft.md`，然后执行章节封存协议，将 `chXX_draft.md` 重命名为正式章节文件 `chXX.md`。

**文件写入规则：**
- 草稿文件命名：`{project_dir}/drafts/chXX_draft.md`（XX 为两位数章节号，如 `ch03_draft.md`）
- 第一段写入时：创建文件并写入章节标题 + 正文
- 第二、三段写入时：append 到同一文件末尾，不覆盖
- 第三段写完、封存协议执行完毕后：将 `{project_dir}/drafts/chXX_draft.md` 重命名为 `{project_dir}/drafts/chXX.md`，草稿文件不再保留

每次输出结束格式（第一、二段用）：
```
---
[PAUSE-X/3 · 第X段已写入 drafts/chXX_draft.md]
[一句话说明当前剧情状态]

A. [走向选项] → [预告]
B. [走向选项] → [预告]
C. [走向选项] → [预告]
（也可以说"继续"直接推进）

发送任意回复继续第X+1段 →
```

**结构**：每次输出 = 正文 + 写作后记

**写作后记仅在第三段（章节最终段）输出。** 第一、二段结束时只输出暂停标记和三分选择，不输出写作后记，避免增加上下文负担。

章节封存协议（更新 session_log、characters、{signal_doc}、continuity、执行编辑审阅）**仅在第三段写入完毕后触发**，触发前先将 `chXX_draft.md` 重命名为 `chXX.md`。

写作后记格式（折叠在正文后，供作者查看）。⚠️ **Showing 检查改为只报命中项**：按题材包 `hooks.md` 的「showing_checklist」逐项自查，但仅输出命中的条目（未命中的项不要打印，清单本身不要复述）：
```
---
【写作后记】
- 本节投放：[描述（线索/信号等投放物），或"无"]
- 角色状态变化：[描述]
- 信息增量：[本节谁新获知了什么关键信息（角色→信息，含来源），或"无"]
- 本节结束时读者已知 / 不知的信息对比：
  已知：...
  不知：...
- Showing 自查（仅列命中项，无命中则写"无"）：
  [按题材包 hooks.md「showing_checklist」自查，命中项标注位置，建议在下一轮 /edit 时修正]
- 下一个三分选择：见下方
---
```

### 三分选择（每次写完后给出）

格式固定：
```
【下一步】

[一句话说明当前剧情状态，读者/主角此刻的处境]

A. [选项]
   → [如果选A，接下来会发生什么，用2句话预告]

B. [选项]  
   → [如果选B...]

C. [选项]
   → [如果选C...]

（或者告诉我你有别的想法）
```

**三分选择的质量标准**：
- 三个选项代表**真正不同的故事走向**，不是同一方向的变体
- 每个选项都有合理的题材内在逻辑
- 不要把"显然正确"的选项放进来——三个都应该有吸引力

## 章节封存协议（第三段写完后强制执行）

> 触发顺序：先将 `chXX_draft.md` 重命名为 `chXX.md`，再依次执行五步；五步全部完成后才进入责任编辑审阅。

### 第一步：更新 meta/session_log.md

按下方"章节摘要日志格式"追加本章条目（必须包含「故事内时间/地点」与「信息增量」字段）。
⚠️ 追加前先确认本章条目不存在（幂等）——严禁重复追加同章摘要或相同的【修改记录】。

### 第二步：更新 meta/characters.md

- 本章出场角色：追加「出场记录」；依据本章「信息增量」更新各角色的「当前已知信息」；更新「当前状态」
- 首次/二次出场判定一律以「出场记录」字段为准

### 第三步：更新 meta/{signal_doc} + 投放预算核对

按题材包 `hooks.md` 的「seal_check」执行：登记本章实际投放的投放物（含正文摘录）并更新状态，完成投放预算核对、结构核对与终章断言，最后回写 outline.md 本章「实际执行」字段。状态变更同步维护「总索引」节（一条不少）。

### 第四步：更新 meta/continuity.md（连贯性登记）

- 「场景登记」表追加本章每个场景一行（章 / 地点 / 氛围视角 / 已用关键细节意象）
- 「事实断言」表追加本章正文新确立的事实（时间线 / 证据结论 / 人物关系变化等，一行一条）
- 格式见下方"连贯性登记格式"；旧项目无此文件时先创建空表再登记

### 第五步：一致性自查（八项清单，逐项核对，发现问题就地修复后再封存）

- [ ] **时间衔接**：本章开头的故事内时间/地点与上一章章末连续（对照 session_log 各章「故事内时间/地点」）
- [ ] **人物位置**：每个场景的在场人物来源可追溯，无凭空出现/消失
- [ ] **物品与身体状态**：上一章末的物品、伤势、衣着、天气等状态延续，无无故重置
- [ ] **称谓一致**：本章所有称呼符合 characters.md 各角色「称谓」字段
- [ ] **角色知识边界**：各角色言行未超出其「当前已知信息」（主角未跳步；他人未说出不该知道的事）
- [ ] **终局一致性**：对照 `{core_doc}`——终局相关角色的公开言行符合其中约定的行为线/时间线（如伪装策略、情感时间线）；叙述未泄露"只有文档持有方知道的信息"
- [ ] **outline 对照**：本章完成计划节点，所有偏差已回写 outline.md
- [ ] **连贯性登记对照**：本章场景与 continuity.md「场景登记」比对——同地点再次进场必须是"有意复访"（推进新内容），不得无意复写既有氛围与细节意象；本章事实不与「事实断言」表冲突，且新增断言已登记入表

## 责任编辑机制（每章自动触发，交互模式）

封存协议五步全部完成后，以编辑身份（题材包 `personas.md`「编辑人格」）重新审阅本章正文，从以下维度输出审阅报告：

- **A. 风格一致性**：对照风格宪法，指出具体漂移位置

- **B. 读者视角模拟**：按题材包 `hooks.md` 的「review_dims」执行（切换至不持有 {core_doc} 的视角）

- **C. 人物声音检查**：逐一核查本章角色对白是否与 characters.md 一致（说话方式 + 称谓；言行是否超出「当前已知信息」边界）

- **D. 问题定级清单**：🔴 必须修改 / 🟡 建议修改 / 🟢 观察记录

审阅完成后，主 agent 对照 `{core_doc}` 过滤意见，标注 `[采纳]` / `[保留]` / `[观察]`，向用户呈现处理后的报告。

> 自动模式的同构审阅由独立 Reviewer 子任务执行（无真相视角），见 `references/auto_agents.md` 第五节。

## `/edit [要求]` — 修改最近段落

**适用场景**：用户对刚生成的段落不满意，想修改

### 支持的修改类型

用户用自然语言描述，你理解并执行：

| 用户说 | 你理解为 |
|--------|----------|
| "这段对话太正式了" | 降低对话的正式程度，增加口语感 |
| "节奏太慢，压缩一下" | 删除冗余描写，保留核心信息，目标字数减少30% |
| "这个角色不像他平时的说话方式" | 对照 characters.md 中该角色的对话风格重写 |
| "把这段扩写，多写环境" | 加入更多感官细节，字数增加50% |
| "投放物太明显了" | 把线索/信号埋得更深，减少叙述者的提示性语言 |

### 执行规范

- 输出时并排显示：**原文 → 修改版**
- 在修改版下方说明修改了什么（1-2句话）
- **meta 同步（强制收尾）**：若改动涉及已投放物的文本/位置、角色状态、称谓、故事内时间线或角色获知的信息 → 同步更新 {signal_doc} / characters.md 对应条目，并在 session_log.md 追加一行：`【修改记录】第X章：{改动要点}`
- 询问是否满意，或继续调整

## `/check_pace [项目名]` — 节奏诊断

**适用场景**：用户怀疑节奏太快/太慢，或连续写作多章后主动体检

### 执行逻辑

```
1. 确认目标项目 {project_dir}，读取 {project_dir}/meta/project_info.md 确认 genre
2. 读取 {project_dir}/meta/session_log.md 最近条目
3. 读取 {project_dir}/meta/{signal_doc} 的投放状态
4. 🔴 按 references/genres/{genre}/craft.md 中「/check_pace 指令逻辑」一节进行诊断
```

## `/solver [项目名]` — 挑战读者测试

**适用场景**：校验误导结构是否真的在读者端生效——读者此刻会得出什么结论？投放物是否"当下可用"？适用于结构转折点（重大反转前后、终局章之前），或用户怀疑"读者早猜到了/读者跟丢了"时。

### 执行逻辑

```
1. 确认目标项目 {project_dir}；完成「槽位解析」
2. 汇总"读者可见语料"（提取规则同 auto_agents.md 6.5，全程不读取 {core_doc}）：
   - session_log.md 各章「核心事件」与「信息状态·读者此刻知道」（蒸馏后的单行历史 + 最近 2 章完整条目）
   - {signal_doc} 中状态为"已投放"的投放物（剔除 🔒 真相指针字段后的公开字段）
3. 以"无终局视角的挑战读者"身份作答：
   - 我此刻的领先推论是什么（可列多个，按可能性排序）？
   - 每条推论的支撑投放物/细节是哪些（可指认）？
   - 信心度（百分比）与最困惑的一点？
4. 切换回作者视角，读取 {core_doc} 对照判定：
   - 领先推论 = 当前应生效的假象/误导结构 → ✅ 结构生效
   - 领先推论 = 终局事实 → ⚠️ 提前泄漏：检查近期投放物指向性是否过强，考虑调整后续投放顺序（更新 outline 并记录原因）
   - 领先推论 = 早已被推翻的旧结构，或无法组织任何推论 → ⚠️ 支撑不足：下章补维持性证据，或让主角做一次梳理
5. 结论以一行【挑战读者测试】条目追加到 {project_dir}/meta/session_log.md
```

### 输出格式

```
【挑战读者测试】（第X章后）

🧠 读者端领先推论：[推论1（信心X%）/ 推论2（X%）...]
🧾 支撑投放物：[编号/细节列表]
❓ 最困惑点：[一句话]

📊 对照判定：[结构生效 / 提前泄漏 / 支撑不足]
💡 建议：[下一章的具体调整（投放/梳理/顺序）]
```

> 自动模式在关键章间自动执行同构测试，命中触发条件（下一章含推翻操作或属收敛/揭示/终局阶段）时为强制项（角色与判定规则见 auto_agents.md 4.4；触发点见本文 /auto-write 执行流程步骤 19.5），无需手动调用。

## 连贯性登记格式（continuity.md）

每章封存第四步追加/更新（题材中立，所有项目共用；初始化时创建空表，见 init_flow.md）：

```markdown
# 《{书名}》连贯性登记

## 场景登记

| 章 | 地点 | 氛围/视角 | 已用关键细节意象 |
|----|------|----------|------------------|
| 1 | [地点] | [氛围基调/叙事视角] | [本场景已用掉的标志性细节，一句话] |

## 事实断言

| 章 | 断言（正文确立的事实） |
|----|------------------------|
| 1 | [时间线 / 证据结论 / 人物关系等，一行一条] |
```

- **场景登记防"无意复写"**：同地点再次进场前先查此表——复访必须推进新内容，氛围与细节意象不得照搬；有意复访（如重回案发现场）应在氛围列体现"变化"
- **事实断言防"逻辑矛盾"**：正文一经确立的事实即入表；后文要推翻必须给出故事内依据（新证据/新视角），不得无声改口
- 表体量控制：每行一句话；不做叙述展开，总表超过 150 行时压缩最早章节的行为"章号+一句话"

## 两轮全稿审阅协议

> 在 `/finish` 执行完毕后自动触发，也可通过 `/review [项目名]` 手动调用。
> 两轮审阅按顺序执行，不可跳过第一轮直接进入第二轮。

### 分块审阅规则（长稿必读）

全稿内联审阅会撑爆单次上下文，按以下规则分块：

```
- 总章节数 ≤ 4：单次执行（主 Agent 直接按下方协议逐轮审阅）
- 总章节数 > 4：分块派发审阅子任务
  - 每块 3-4 章，相邻块重叠 1 章（用于捕捉跨块矛盾）
  - 第一轮块子任务注入：块内章节全文 + {core_doc} + characters.md + style_guide.md
  - 第二轮块子任务注入：块内章节全文（⚠️ 不含 {core_doc}，保持编辑新鲜视角）
  - Director 汇总各块报告：去重相邻块重复项、复核跨块矛盾
  - 第二轮的全书级判断（核心判断/读者体验预判/如果只能改一件事）由 Director 基于各块报告综合得出，不要求单个块子任务回答
  - 无子任务机制的运行环境：主 Agent 分块顺序自审（同样重叠 1 章），禁止一次性内联全部章节
```

---

### 第一轮：全稿一致性核查

**目标**：扫描跨章节的逻辑矛盾、称呼漂移、时代感失真。
**视角**：持有 `{core_doc}`，以作者身份检查。
**输入**：全部 `{project_dir}/drafts/chXX.md` 文件 + `{project_dir}/meta/characters.md` + `{project_dir}/meta/style_guide.md`

逐章扫描，重点检查以下五类问题：

**A. 前后逻辑矛盾**
- 人物在某章确认的事实，后续章节是否出现不一致的陈述？
- 时间线是否有冲突？以各章 session_log 的「故事内时间/地点」字段为基准逐章排检（例如：某人在第3章"三天前"做了某事，但第7章的时间线对不上）
- 角色知识边界是否被穿越？（对照 characters.md 各章末的「当前已知信息」：主角是否使用了未获知的信息，他人是否说出不该知道的事）
- 已拆穿/化解的反向投放物，后续是否意外"复活"？

**B. 称呼与关系漂移**
- 人物之间的称呼是否前后一致？（例如：从正式称谓突然变成昵称，但没有对应的关系发展情节）
- 人物对彼此的态度转变，是否有场景支撑？

**C. 时代感失真**
- 对照 `meta/style_guide.md` 中的语言禁忌，标记所有疑似时代感漂移的对白或叙述
- 当代概念出现在历史背景中，或反之

**D. 角色声音漂移**
- 对照 `characters.md` 中每个角色的说话方式，标记风格明显不符的对白

**E. 题材专项核查**
- 按题材包 `hooks.md`「full_review」的**第一轮专项核查项**执行（跨章节的题材结构核查）

**输出格式**：

```
【第一轮审阅：一致性核查】

🔴 必须处理（X条）
- [章节] [类型] [具体问题描述] → 建议方向

🟡 建议处理（X条）
- [章节] [类型] [具体问题描述] → 建议方向

🟢 观察记录（X条）
- [章节] [类型] [描述]（不影响阅读，但可在修订时考虑）

（如无问题，输出"✅ 全稿一致性检查通过，未发现明显矛盾"）
```

第一轮输出完毕后，自动进入第二轮。

---

#### 第二轮：文学编辑评审

按题材包 `hooks.md`「full_review」的**第二轮输出格式**执行（目标 / 视角 / 输入 / 输出维度模板均以题材包定义为准；编辑人格取题材包 `personas.md`）。

**评审执行纪律**：
- 禁止在没有文本依据的情况下夸赞"文笔优美"、"人物立体"
- 禁止为了平衡而强行加入夸奖或批评
- 禁止用"这只是个人意见"稀释判断
- 如果某个维度确实没有意见，直接跳过，不凑字数

```
【审阅完成】

以上问题共涉及 X 处需修改内容。
```

3. 进入 `/edit` 流程，等待用户确认或进一步调整
4. 修改完成后，更新 `{project_dir}/drafts/chXX.md`，并在 `{project_dir}/meta/session_log.md` 中追加修改记录

## `/auto-write [项目名|new]` — 自动写作模式

> 详细角色定义、Prompt 模板和通信协议见 `references/auto_agents.md`。
> 四角色协作：Director（编排核验）/ Writer（写正文）/ Chooser（读者视角选走向）/ Reviewer（无真相视角审阅）；另有 Solver（挑战读者测试，按需触发，见 auto_agents.md 4.4）。

### 前置检查与项目锁定（必须通过才能开始）

```
1. 目标判定：
   - 若参数为 new（如 /auto-write new）：
     a. 调用 references/init_flow.md 引导用户完成前置选择与各轮共创对话
     b. 按 references/genres/{genre}/init.md 的文件生成清单生成 novels/{项目名}/ 及其下 meta/ 和 drafts/ 文件
     c. 锁定 {project_dir} = novels/{项目名}
     d. 初始化完毕后【自动无缝启动】全书自动写作流水线（从第1章开始）
   - 若参数指定了项目名/路径（如 /auto-write 倒影的碎片）：
     锁定 {project_dir} = novels/{项目名}
   - 若未指定且当前无上下文：
     列出 novels/ 下的一级小说目录供用户选择（或输入 new）；严禁擅自挑选！
2. 读取 {project_dir}/meta/project_info.md 获取 genre、language；按「槽位解析」加载题材包 manifest（+ personas.md / hooks.md，供构建子任务 prompt）
3. 确认 {project_dir}/meta/ 目录下所有必要文件存在（project_info, style_guide, {core_doc}, characters, {signal_doc}, outline, session_log, continuity——旧项目缺 continuity.md 时创建空表，格式见本文「连贯性登记格式」）
4. 读取 {project_dir}/meta/outline.md 确定总章节数
5. 读取 {project_dir}/meta/session_log.md 并检查 {project_dir}/drafts/ 确定当前进度（已完成的章节数）
6. 【中断恢复】检查断点（见 auto_agents.md 6.7）：
   - 若存在 chXX_draft.md 残留（1-2段）→ 从第 XX 章第 (段数+1) 段续写，不作废不重写
   - 读取 meta/auto_state.json 恢复 chooser_log；缺失则从 session_log 重建（选择轨迹可缺省）
   - 向用户报告恢复点
7. 初始化/更新 meta/auto_state.json（mode、total_chapters、恢复的 chooser_log）
8. 向用户确认并汇报初始状态："《{书名}》将从第 X 章自动写到第 Y 章（共 Z 章），启动自动化写作循环..."
```

### 执行流程

Director（主 Agent 自身）按以下循环执行（输出核验规则见 auto_agents.md 6.4）：

```
对于每一章 (chapter = 恢复点或当前进度+1 到 总章数):

  ── 章间检查点（第2章起）──
  0. 处理上帝指令与停止条件（见下方"运行期干预"）
  0.5 章间维护：meta 蒸馏（见 auto_agents.md 6.8）

  ── 段落 1 ──
  1. 按 auto_agents.md 6.1 模板构建 Writer prompt
     （注入：身份[题材包 personas] + 风格 + {core_doc} + 角色 + 投放物状态 + outline + 上章尾 + 上帝指令 + 题材钩子[hooks]）
  2. 派发 Writer 子任务
  3. 【核验】draft 文件增长 + 字数达标（zh 850-950字 / en 550-650词）+ <choices> 可解析 + 选项公平
     失败 → 按 auto_agents.md 6.4 轻量补救（补写/重发缺失标签/代写文件），不盲信报告
  4. 构建 Chooser prompt（前情 + 本章摘要 + 选择轨迹，⚠️ 绝不含 {core_doc}，见 auto_agents.md 6.2）
  5. 派发 Chooser 子任务
  6. 【核验】<choice> ∈ {A,B,C}；记录到 auto_state.json 的 chooser_log

  ── 段落 2 ──
  7-10. 同段落 1，Writer prompt 追加 Chooser 的第1段走向选择 + 当前草稿全文

  ── 段落 3（收拢 + 封存，Writer 只写不审）──
  11. 构建 Writer prompt（第3段模板：收拢本章 + 执行封存协议，不含编辑审阅）
  12. 派发 Writer 子任务
  13. 【核验】drafts/chXX.md 已重命名（否则 Director 代做 mv；并确认 chXX_draft.md 残留已清除）；
      <seal_report> 中 failed 的 meta 更新由 Director 补写

  ── 责任编辑审阅（独立 Reviewer，无真相视角）──
  14. 按 auto_agents.md 6.3 构建 Reviewer prompt（脱敏上下文：正文 + 风格 + 脱敏角色条目 + 已投放物）
  15. 派发 Reviewer 子任务
  16. 【核验】<review_report> 可解析；失败重试1次，仍失败则本章跳过审阅并标记 ⚠️

  ── 审阅过滤与自动修复（有界循环）──
  17. Director 对照 {core_doc} 过滤报告：[采纳] / [保留] / [观察]
  18. [采纳]且🔴 → 派发 Writer 修复子任务（附风格+角色上下文）→ 核验 applied=yes
      同一问题最多 2 轮；仍失败 → 降级为 🟡，继续推进，不阻断
  19. 🟡（含降级条目）→ 封存完成后追加记录到 {project_dir}/meta/session_log.md
      🟢 → 忽略

  ── 挑战读者测试（Solver，🔴 命中触发条件即强制执行，非可选诊断）──
  19.5 判定触发条件：读取 outline.md 第 N+1 章计划，若其结构操作含「推翻」（假设/主线转折），
       或第 N+1 章属于证据收敛/推导揭示/终局阶段
       → 按 auto_agents.md 4.4 构建 Solver prompt（摘要版上下文）并派发子任务（不得跳过；跳过须在 session_log 记录原因）
       → 【核验】<solver_report> 可解析；失败重试1次，仍失败跳过并在本章进度卡片标记 ⚠️（不阻断）
       → 按 4.4 判定规则对照 {core_doc} 得出结论（结构生效/提前泄漏/支撑不足），
         封存完成后以【挑战读者测试】条目追加 session_log；需调整后续投放顺序时
         更新 outline「章节计划变更记录」并写明原因

  ── 进度汇报 ──
  20. 向用户输出本章完成状态与进度看板
  21. 检查停止条件（用户要求停 / 达到指定章数）→ 满足则输出结算看板并停止
  22. 更新 auto_state.json，继续下一章

全部章节完成后：
  23. 汇总 session_log 中全部 🟡/降级🔴 条目，输出《待处理建议清单》（自动模式不自动修复🟡）
  24. 执行 /finish（按序合并所有 {project_dir}/drafts/chXX.md 为完整小说文件）
  25. 自动触发两轮全稿审阅（分块协议见上方"两轮全稿审阅协议"）
  26. 全稿审阅中 [采纳]+🔴 的问题自动派发 Writer 修复（同样有界：最多2轮，失败降级🟡）
  27. 向用户输出最终完成报告（含《待处理建议清单》与批量处理提示）
```

### 运行期干预（上帝指令与暂停）

自动写作运行期间，用户随时可以直接输入自然语言消息（无需等待暂停）。Director 在**每个章间检查点**处理未消费的用户消息：

```
1. 内容类指令（如"第5章前让角色X正式出场"、"节奏太慢，压缩支线"）：
   - 与 {core_doc} 不冲突 → 写入 {project_dir}/meta/directives.md，
     在后续 Writer prompt 的"上帝指令"节注入
   - 与核心设定冲突（如指定了与 {core_doc} 相悖的终局事实）→ 标记为 blocked，
     在本章进度看板中提示用户；致命冲突则暂停等待用户确认
2. 停止类指令（"/auto-pause"、"停下来"、"先停一下"）：
   → 当前章节流水线完整走完后停止，输出结算看板与恢复方式
3. 范围类指令（"写到第8章停"）：
   → 更新停止条件，写入 auto_state.json
4. 所有已处理的指令在 directives.md 中标记状态（done / blocked / pending）
```

`/auto-pause [项目名]` 为显式暂停指令：若自动流水线正在运行，等效于上述停止类指令；若已停止，仅输出当前状态与恢复方式（`/auto-write` 从断点续写）。

### 进度汇报格式

每章完成后，Director 向用户输出**单行**进度（⚠️ 不逐章重列已完成章节——每章重新罗列全部历史章节会随进度线性膨胀上下文）：

```
📖 《{书名}》 {已完成章数}/{总章数} ({百分比}%) | 最新：✅ 第{X}章 ({字数}字) — Chooser: [{路径}] — 审阅: {🔴×n 🟡×n 🟢×n / ⚠️} | ⏳ 下一章：第{X+1}章
（如有 blocked 的上帝指令，在下方单独列出提示）
```

### 异常处理

异常场景的完整处理机制以 `references/auto_agents.md` 为准（第二节"解析失败处理"与 6.4"输出核验协议"为唯一权威定义）：轻量重试优先于整任务重跑、Chooser 失败默认选 A、Reviewer 失败跳过本章审阅标记 ⚠️、修复循环最多 2 轮后降级 🟡 不阻断主流程。

补充一条本文件专属规则：
- **上下文过长** → 章间蒸馏（见 auto_agents.md 6.8）：session_log 压缩、投放物归档、characters 状态快照化

## `/auto-chapter [项目名|new]` — 单章自动写作

与 `/auto-write` 采用相同的 Director / Writer / Chooser / Reviewer 四角色协作机制（含输出核验、有界修复循环、auto_state.json 检查点），但执行范围仅限定为**当前正在进行的这一个章节**。

### 执行流程

1. 执行 `/auto-write` 相同的前置检查与项目锁定（含中断恢复；若为 `new` 则先初始化并自动写完第1章）
2. 仅执行当前单章的写作流水线（第1段 → Chooser → 第2段 → Chooser → 第3段收拢 + 章节封存 → Reviewer 审阅 → 过滤 → 🔴有界自动修复）
3. 章节完成后更新 auto_state.json，输出本章结算看板与决策提示：

```
✅ 第 {N} 章 自动写作完成 ({字数}字)

Chooser 选择路径：{段1选择} → {段2选择} → 收拢
审阅结果：{🔴×0 🟡×1 🟢×2}（🔴 已自动修复 {n} 处；降级 {m} 处）

下一步可选：
- 输入 /auto-chapter 继续自动写下一章
- 输入 /auto-write 自动写完剩余全部章节
- 输入 /write 切回交互式单段手动共创
- 输入 /plan 先讨论后续章节架构
- 说"批量处理🟡" 逐条修复本章记录的建议问题
```

## `/auto-pause [项目名]` — 暂停自动写作

**适用场景**：自动写作流水线运行中或已停止时，请求暂停 / 查看恢复方式

### 执行逻辑

```
1. 确认目标项目 {project_dir}
2. 若自动流水线正在运行：注册停止条件——当前章节流水线完整走完后停止
   （不中断本章，保证章节完整性：写完当前段落的收拢、封存、审阅、修复）
3. 若已停止：输出当前断点状态与恢复方式
4. 停止时输出结算看板：
   - 已完成章节列表与审阅统计
   - 断点位置（第 X 章第 X 段 / 章间）
   - 未消费的上帝指令（若有）
   - 恢复方式："输入 /auto-write {项目名} 从断点续写"
```
