# 写作循环：指令行为定义

## 目标项目锁定协议（每次指令前必读）

在执行本文件任何指令（`/write`, `/plan`, `/status`, `/clue`, `/edit`, `/recap`, `/finish`, `/review`, `/auto-write`, `/auto-chapter`, `/auto-pause`）前，必须先确定目标小说目录 `{project_dir}`（即 `novels/{项目名}`）：

1. **参数为 `new`**（如 `/auto-write new`、`/write new`）：跳转到 `references/init_flow.md` 执行初始化流程（遵守其"交互停止契约"：4轮问答与基本信息收集由真实用户逐轮回答；若来自 `/auto-write new`，初始化完成后自动无缝进入第1章自动写作）。
2. **参数包含项目名/路径**（如 `/auto-write 倒影的碎片`、`/write novels/雪祭`）：锁定 `{project_dir} = novels/{项目名}`。
3. **会话已有上下文**：沿用当前会话已锁定的 `{project_dir}`。
4. **未指定且存在多部小说**：仅列出 `novels/` 下的一级目录名，询问用户需要操作哪部小说或创建 `new`。**严禁擅自选择！**
5. ⚠️ **隔离红线**：所有读写只能在 `{project_dir}` 内进行，**绝对严禁**扫描、读取或修改 `novels/` 下其他未锁定的兄弟小说目录。

## `/write [项目名|new]` — 推进剧情

### 执行前准备（必须完成，按顺序）

**第0步：确定目标项目与当前段落编号（每次 /write 必须先做这一步）**

1. 确认已锁定 `{project_dir}`（若指令为 `/write new` 则转入初始化流程）
2. 检查 `{project_dir}/drafts/chXX_draft.md` 是否存在：
- 文件不存在 → 当前为**第1段**，本次 /write 将创建文件
- 文件存在，内容只有1段（约900字）→ 当前为**第2段**
- 文件存在，内容有2段（约1800字）→ 当前为**第3段（最终段）**

判断完成后，在内心确认："本次我将写第X/3段"，并以此决定本次输出的结束行为（暂停 or 封存协议）。

```
0. 读取 {project_dir}/meta/project_info.md，获取 genre 和 language 字段
   - genre: mystery → 执行推理版逻辑（以下步骤1-6不变）
   - genre: romance → 执行爱情版逻辑（步骤2替换，步骤3字段调整，见下方）
   - language: zh / en → 确认本次 /write 输出语言

1. 读取 {project_dir}/meta/style_guide.md（仅加载"绝对禁止"和"样板句式"两节）

2. [mystery] 读取 {project_dir}/meta/truth.md（提醒自己不能泄露的信息）
   [romance] 读取 {project_dir}/meta/relationship_arc.md（关系弧线文档，了解当前章节的情感状态目标）

3. 读取 {project_dir}/meta/characters.md（本章出场角色）
   ⚠️ 首次出场角色只加载以下字段：
   - 出场前读者已知信息
   - 出场引入方式
   - 身份（仅职业/社会角色）
   [mystery] 完整档案（性格、动机、隐瞒的事）须在该角色二次出场后才解锁。
   [romance] 完整档案（性格、情感盲区、情感起点）须在该角色二次出场后才解锁。
   ⚠️ 首次/二次出场的判定一律以角色条目中的「出场记录」字段为准（不由记忆判断）。

4. [mystery] 读取 {project_dir}/meta/clues.md（已投放 / 待投放线索）
   [romance] 读取 {project_dir}/meta/romance_clues.md（情感信号投放状态）

5. 若 {project_dir}/drafts/chXX_draft.md 存在：读取全文（衔接 + 确认段落数）；否则读取上一章 chXX.md 最后 500 字

6. 读取 {project_dir}/meta/session_log.md 最近 2 章条目（核心事件、角色变化、故事内时间/地点、信息增量、下章切入点）——这是跨章衔接与一致性核对的基准；即使第5步已读本章草稿也必须读取

7. 读取 {project_dir}/meta/outline.md 中本章的计划节点（本章目标、应投线索、假设操作、应揭秘密、应拆穿误导、章末钩子）
```

### 写作前行为预检

[mystery] 在涉及凶杀或高风险对抗的场景前，先用一句话回答：
"[受害者]此时的信息量是[X]，他/她的求生本能和处事逻辑，会让他/她做出什么行为？"
如果计划中的剧情与这个答案冲突，必须调整触发条件（让场景在更高的张力点爆发），而不是降低人物智识。

[romance] 在涉及情感决定性转折（表白/分离/和解）的场景前，先用一句话回答：
"[角色名]此时对对方的真实认知是[X]，他/她的情感逻辑和自我保护机制，会让他/她做出什么行为？"
如果计划中的剧情要求角色做出与其情感逻辑不符的行为，必须先补写情感积累，让转变有迹可循。

### 写作规范

**字数与节奏**：每章目标 zh 约 2700 字 / en 约 1800 词，分三段推进，每段 zh 约 900 字 / en 约 600 词。

⚠️ 字数硬约束（每段写完后必须自查）：
- 每段目标范围：zh 850–950 字 / en 550–650 词（按 language 字段选择标准）
- 低于下限：禁止输出 PAUSE 标记，必须补写至达标
- 超过上限：检查是否有可拆入下一段的内容，若无则允许保留
- 自查方式：输出正文后，在内心估算段落字数/词数，不达标则继续写，不得以"段落自然结束"为由提前停止

**重要：每次 `/write` 只生成一段。** 模型不自行连续生成三段——暂停由对话结构保证，而非模型自我中断。

**第一段（约900字）**：开场，推进到一个"信息悬停点"后结束本次输出，将本段正文 **append 写入** `{project_dir}/drafts/chXX_draft.md`，然后给出三分选择，等待用户回应。
**第二段（约900字）**：根据用户在第一段后的选择推进，到"张力转折点"后结束本次输出，将本段正文 **append 写入** 同一 `{project_dir}/drafts/chXX_draft.md`，给出三分选择，等待用户回应。
**第三段（约900字）**：收拢本章，以"悬而未决的尾音"结束——不解答，提出下一章的核心问题。将本段正文 **append 写入** 同一 `{project_dir}/drafts/chXX_draft.md`，然后执行章节封存协议，将 `chXX_draft.md` 重命名为正式章节文件 `chXX.md`。

**文件写入规则：**
- 草稿文件命名：`{project_dir}/drafts/chXX_draft.md`（XX 为两位数章节号，如 `ch03_draft.md`）
- 第一段写入时：创建文件并写入章节标题 + 正文
- 第二、三段写入时：append 到同一文件末尾，不覆盖
- 第三段写完、封存协议执行完毕后：将 `{project_dir}/drafts/chXX_draft.md` 重命名为 `{project_dir}/drafts/chXX.md`，草稿文件不再保留

每次输出结束格式（第一、二段用）：
```
---
[PAUSE-X/3 · 第X段已写入 drafts/chXX_draft.md]
[一句话说明当前剧情状态]

A. [走向选项] → [预告]
B. [走向选项] → [预告]
C. [走向选项] → [预告]
（也可以说"继续"直接推进）

发送任意回复继续第X+1段 →
```

**结构**：每次输出 = 正文 + 写作后记

**写作后记仅在第三段（章节最终段）输出。** 第一、二段结束时只输出暂停标记和三分选择，不输出写作后记，避免增加上下文负担。

章节封存协议（更新 session_log、characters、clues、执行编辑审阅）**仅在第三段写入完毕后触发**，触发前先将 `chXX_draft.md` 重命名为 `chXX.md`。

写作后记格式（折叠在正文后，供作者查看）：
```
---
【写作后记】
- 本节投放线索：[描述，或"无"]
- 角色状态变化：[描述]
- 信息增量：[本节谁新获知了什么关键信息（角色→信息，含来源），或"无"]
- 本节结束时读者已知 / 不知的信息对比：
  已知：...
  不知：...
- Showing 检查：本节是否出现以下任一情况？
  □ 叙述者直接说明人物的情绪（"她是在恐惧"而非"她的手按住了椅背"）
  □ 人物说出当代/时代不会说的哲理句

  [mystery 专项]
  □ 侦探"判断出/意识到/感觉到"某结论（而非通过行为展示）
  □ 侦探得出结论时未引用可指认的已投放线索（凭直觉宣布，跳过观察→疑问→验证→判断）
  □ 出现人物整段讲述真相/证据性信息的自白（讲解模式；动机与情感的简短吐露除外）
  □ 凶手（以嫌疑人身份出场时）的言行偏离 truth.md 的伪装策略
  □ 叙述或他人对白泄露了"只有凶手知道的信息"
  □ 侦探言行超出 characters.md 中其「当前已知信息」的边界

  [romance 专项]
  □ 角色直接说出自己的感情状态（"我意识到我喜欢他了"——应改为行为/细节暗示）
  □ 感情障碍在没有充分积累的前提下突然消解
  □ 对话里的两个人，说的话和他们内心想法完全一致（真实的人在情感场合说话总是保留）

  如有，标注位置，建议在下一轮 /edit 时修正。
- 下一个三分选择：见下方
---
```

### 三分选择（每次写完后给出）

格式固定：
```
【下一步】

[一句话说明当前剧情状态，读者/侦探此刻的处境]

A. [选项]
   → [如果选A，接下来会发生什么，用2句话预告]

B. [选项]  
   → [如果选B...]

C. [选项]
   → [如果选C...]

（或者告诉我你有别的想法）
```

**三分选择的质量标准**：
- 三个选项代表**真正不同的故事走向**，不是同一方向的变体
- 每个选项都有合理的推理小说内在逻辑
- 不要把"显然正确"的选项放进来——三个都应该有吸引力

## 章节封存协议（第三段写完后强制执行）

> 触发顺序：先将 `chXX_draft.md` 重命名为 `chXX.md`，再依次执行四步；四步全部完成后才进入责任编辑审阅。

### 第一步：更新 meta/session_log.md

按下方"章节摘要日志格式"追加本章条目（必须包含「故事内时间/地点」与「信息增量」字段）。

### 第二步：更新 meta/characters.md

- 本章出场角色：追加「出场记录」；依据本章「信息增量」更新各角色的「当前已知信息」；更新「当前状态」
- 首次/二次出场判定一律以「出场记录」字段为准

### 第三步：更新 meta/clues.md + 线索预算核对

- 登记本章实际投放的线索（含正文摘录），更新状态
- **线索预算核对（对照 outline.md 本章计划）**：
  - 计划投放的 CL-/RH- 是否已投？未投 → 就地补投，或显式修改 outline 计划并在「章节计划变更记录」中写明原因。**禁止无声遗漏**
  - 计划揭示的嫌疑人秘密是否已揭？计划拆穿的 RH 是否已拆穿？同上
- **假设链核对**：对照 outline.md 本章「假设操作」——计划建立/强化/推翻的 H-X 是否完成？推翻是否由证据驱动（可指认 CL-XX，而非说漏嘴/巧合/自白）？未完成 → 就地补写，或显式修改 outline 计划并记录原因。**禁止无声遗漏**
- **揭示章断言（双断言）**：若下一章进入真相揭示（outline 中第三幕收拢/结局章）：
  - 逐条断言所有 Hard Clues 状态为"已投放"——未投放的必须在本章内补投
  - 逐条断言 truth.md 假真相设计中所有 H 均已按计划建立并被证据推翻——有缺口的在本章内补齐（该补的推翻必须由证据完成）
- 回写 outline.md 本章「实际执行」字段（已完成 / 偏差及原因）

### 第四步：一致性自查（七项清单，逐项核对，发现问题就地修复后再封存）

- [ ] **时间衔接**：本章开头的故事内时间/地点与上一章章末连续（对照 session_log 各章「故事内时间/地点」）
- [ ] **人物位置**：每个场景的在场人物来源可追溯，无凭空出现/消失
- [ ] **物品与身体状态**：上一章末的物品、伤势、衣着、天气等状态延续，无无故重置
- [ ] **称谓一致**：本章所有称呼符合 characters.md 各角色「称谓」字段
- [ ] **角色知识边界**：各角色言行未超出其「当前已知信息」（侦探未跳步；嫌疑人未说出不该知道的事）
- [ ] **[mystery] 凶手一致性**：凶手的公开言行符合 truth.md 伪装策略与案发后行为线；叙述未泄露"只有凶手知道的信息"
- [ ] **outline 对照**：本章完成计划节点，所有偏差已回写 outline.md

## `/clue [描述]` — 植入线索

**适用场景**：用户想在下一段正文中植入一条特定线索或伏笔

### 执行逻辑

```
1. 接收用户的线索/信号描述
2. [mystery] 判断线索类型：关键线索 / 误导线索 / 氛围线索
   [romance] 判断信号类型：ES（情感信号）/ DS（退缩信号）/ AS（氛围信号）
3. 在下一段正文中自然植入（不特意强调）
4. 写作后立即更新 {project_dir}/meta/clues.md（mystery）或 {project_dir}/meta/romance_clues.md（romance）
```

### 植入原则

[mystery]
- **不能让线索显得"孤立"**：线索要包裹在场景动作或对话里
- **不能让侦探立刻注意到**（除非是第10章以后的揭示阶段）
- 植入后在写作后记中注明："本节植入线索：[描述]"

[romance]
- **信号必须包裹在日常行为/对话里**，不是特写镜头
- ES 与 DS 交替投放才有重量——靠近之后需要退缩
- 植入后在写作后记中注明："本节植入信号：[编号与描述]"

## `/edit [要求]` — 修改最近段落

**适用场景**：用户对刚生成的段落不满意，想修改

### 支持的修改类型

用户用自然语言描述，你理解并执行：

| 用户说 | 你理解为 |
|--------|----------|
| "这段对话太正式了" | 降低对话的正式程度，增加口语感 |
| "节奏太慢，压缩一下" | 删除冗余描写，保留核心信息，目标字数减少30% |
| "这个角色不像他平时的说话方式" | 对照 characters.md 中该角色的对话风格重写 |
| "把这段扩写，多写环境" | 加入更多感官细节，字数增加50% |
| "线索太明显了" | 把线索埋得更深，减少叙述者的提示性语言 |

### 执行规范

- 输出时并排显示：**原文 → 修改版**
- 在修改版下方说明修改了什么（1-2句话）
- **meta 同步（强制收尾）**：若改动涉及已投放线索的文本/位置、角色状态、称谓、故事内时间线或角色获知的信息 → 同步更新 clues.md / characters.md 对应条目，并在 session_log.md 追加一行：`【修改记录】第X章：{改动要点}`
- 询问是否满意，或继续调整

## `/recap [N]` — 回顾摘要

**适用场景**：恢复写作前，或用户忘记了最近的情节

### 执行逻辑

读取 `{project_dir}/meta/session_log.md` 中最近 N 章的条目（默认 N=3），整合输出：

```
【最近X章回顾】

第X章：[核心事件，2-3句话]
第X+1章：[核心事件]
第X+2章（最新）：[核心事件]
```

## 两轮全稿审阅协议

> 在 `/finish` 执行完毕后自动触发，也可通过 `/review [项目名]` 手动调用。
> 两轮审阅按顺序执行，不可跳过第一轮直接进入第二轮。

### 分块审阅规则（长稿必读）

全稿内联审阅会撑爆单次上下文，按以下规则分块：

```
- 总章节数 ≤ 4：单次执行（主 Agent 直接按下方协议逐轮审阅）
- 总章节数 > 4：分块派发审阅子任务
  - 每块 3-4 章，相邻块重叠 1 章（用于捕捉跨块矛盾）
  - 第一轮块子任务注入：块内章节全文 + truth.md / relationship_arc.md + characters.md + style_guide.md
  - 第二轮块子任务注入：块内章节全文（⚠️ 不含 truth/arc，保持编辑新鲜视角）
  - Director 汇总各块报告：去重相邻块重复项、复核跨块矛盾
  - 第二轮的全书级判断（核心判断/读者体验预判/如果只能改一件事）由 Director 基于各块报告综合得出，不要求单个块子任务回答
  - 无子任务机制的运行环境：主 Agent 分块顺序自审（同样重叠 1 章），禁止一次性内联全部章节
```

---

### 第一轮：全稿一致性核查

**目标**：扫描跨章节的逻辑矛盾、称呼漂移、时代感失真。
**视角**：持有 `truth.md`，以作者身份检查。
**输入**：全部 `{project_dir}/drafts/chXX.md` 文件 + `{project_dir}/meta/characters.md` + `{project_dir}/meta/style_guide.md`

逐章扫描，重点检查以下四类问题：

**A. 前后逻辑矛盾**
- 人物在某章确认的事实，后续章节是否出现不一致的陈述？
- 时间线是否有冲突？以各章 session_log 的「故事内时间/地点」字段为基准逐章排检（例如：某人在第3章"三天前"做了某事，但第7章的时间线对不上）
- 角色知识边界是否被穿越？（对照 characters.md 各章末的「当前已知信息」：侦探是否使用了未获知的信息，嫌疑人是否说出不该知道的事）
- 已拆穿的误导线索，后续是否意外"复活"？

**B. 称呼与关系漂移**
- 人物之间的称呼是否前后一致？（例如：从正式称谓突然变成昵称，但没有对应的关系发展情节）
- 人物对彼此的态度转变，是否有场景支撑？

**C. 时代感失真**
- 对照 `meta/style_guide.md` 中的语言禁忌，标记所有疑似时代感漂移的对白或叙述
- 当代概念出现在历史背景中，或反之

**D. 角色声音漂移**
- 对照 `characters.md` 中每个角色的说话方式，标记风格明显不符的对白

**E. 假设链核查（mystery 专项）**
- 假真相（H1/H2）是否真实建立过——读者是否曾有机会相信并投入一个错误解释？
- 每个 H 是否被证据推翻（而非被作者遗忘、被自白取代、或从未真正成立）？
- 侦探全书是否至少一次当着读者推翻自己？
- 揭示章是推导式还是讲解式？侦探引用的每条证据是否均已投放（clues.md 可查）？自白是否越界承担了证据功能？
- 过去/背景信息是否以当前证据形态分散浮出？是否存在终章"历史故事块"式的集中倾倒？
- 推理/发现/反转场景中，气氛描写是否打断了推理节奏？

**输出格式**：

```
【第一轮审阅：一致性核查】

🔴 必须处理（X条）
- [章节] [类型] [具体问题描述] → 建议方向

🟡 建议处理（X条）
- [章节] [类型] [具体问题描述] → 建议方向

🟢 观察记录（X条）
- [章节] [类型] [描述]（不影响阅读，但可在修订时考虑）

（如无问题，输出"✅ 全稿一致性检查通过，未发现明显矛盾"）
```

第一轮输出完毕后，自动进入第二轮。

## `/auto-write [项目名|new]` — 自动写作模式

> 详细角色定义、Prompt 模板和通信协议见 `references/auto_agents.md`。
> 四角色协作：Director（编排核验）/ Writer（写正文）/ Chooser（读者视角选走向）/ Reviewer（无真相视角审阅）。

### 前置检查与项目锁定（必须通过才能开始）

```
1. 目标判定：
   - 若参数为 new（如 /auto-write new）：
     a. 调用 references/init_flow.md 引导用户完成前置选择与4轮对话
     b. 生成 novels/{项目名}/ 及其下 meta/ 和 drafts/ 文件
     c. 锁定 {project_dir} = novels/{项目名}
     d. 初始化完毕后【自动无缝启动】全书自动写作流水线（从第1章开始）
   - 若参数指定了项目名/路径（如 /auto-write 倒影的碎片）：
     锁定 {project_dir} = novels/{项目名}
   - 若未指定且当前无上下文：
     列出 novels/ 下的一级小说目录供用户选择（或输入 new）；严禁擅自挑选！
2. 确认 {project_dir}/meta/ 目录下所有必要文件存在（project_info, style_guide, truth/relationship_arc, characters, clues/romance_clues, outline, session_log）
3. 读取 {project_dir}/meta/project_info.md 获取 genre、language
4. 读取 {project_dir}/meta/outline.md 确定总章节数
5. 读取 {project_dir}/meta/session_log.md 并检查 {project_dir}/drafts/ 确定当前进度（已完成的章节数）
6. 【中断恢复】检查断点（见 auto_agents.md 6.7）：
   - 若存在 chXX_draft.md 残留（1-2段）→ 从第 XX 章第 (段数+1) 段续写，不作废不重写
   - 读取 meta/auto_state.json 恢复 chooser_log；缺失则从 session_log 重建（选择轨迹可缺省）
   - 向用户报告恢复点
7. 初始化/更新 meta/auto_state.json（mode、total_chapters、恢复的 chooser_log）
8. 向用户确认并汇报初始状态："《{书名}》将从第 X 章自动写到第 Y 章（共 Z 章），启动自动化写作循环..."
```

### 执行流程

Director（主 Agent 自身）按以下循环执行（输出核验规则见 auto_agents.md 6.4）：

```
对于每一章 (chapter = 恢复点或当前进度+1 到 总章数):

  ── 章间检查点（第2章起）──
  0. 处理上帝指令与停止条件（见下方"运行期干预"）
  0.5 章间维护：meta 蒸馏（见 auto_agents.md 6.8）

  ── 段落 1 ──
  1. 按 auto_agents.md 6.1 模板构建 Writer prompt
     （注入：身份 + 风格 + truth/arc + 角色 + 线索 + outline + 上章尾 + 上帝指令）
  2. 派发 Writer 子任务
  3. 【核验】draft 文件增长 + 字数达标（zh 850-950字 / en 550-650词）+ <choices> 可解析 + 选项公平
     失败 → 按 auto_agents.md 6.4 轻量补救（补写/重发缺失标签/代写文件），不盲信报告
  4. 构建 Chooser prompt（前情 + 本章摘要 + 选择轨迹，⚠️ 绝不含 truth/arc，见 auto_agents.md 6.2）
  5. 派发 Chooser 子任务
  6. 【核验】<choice> ∈ {A,B,C}；记录到 auto_state.json 的 chooser_log

  ── 段落 2 ──
  7-10. 同段落 1，Writer prompt 追加 Chooser 的第1段走向选择 + 当前草稿全文

  ── 段落 3（收拢 + 封存，Writer 只写不审）──
  11. 构建 Writer prompt（第3段模板：收拢本章 + 执行封存协议，不含编辑审阅）
  12. 派发 Writer 子任务
  13. 【核验】drafts/chXX.md 已重命名（否则 Director 代做）；
      <seal_report> 中 failed 的 meta 更新由 Director 补写

  ── 责任编辑审阅（独立 Reviewer，无真相视角）──
  14. 按 auto_agents.md 6.3 构建 Reviewer prompt（脱敏上下文：正文 + 风格 + 脱敏角色条目 + 已投放线索）
  15. 派发 Reviewer 子任务
  16. 【核验】<review_report> 可解析；失败重试1次，仍失败则本章跳过审阅并标记 ⚠️

  ── 审阅过滤与自动修复（有界循环）──
  17. Director 对照 truth.md / relationship_arc.md 过滤报告：[采纳] / [保留] / [观察]
  18. [采纳]且🔴 → 派发 Writer 修复子任务（附风格+角色上下文）→ 核验 applied=yes
      同一问题最多 2 轮；仍失败 → 降级为 🟡，继续推进，不阻断
  19. 🟡（含降级条目）→ 封存完成后追加记录到 {project_dir}/meta/session_log.md
      🟢 → 忽略

  ── 进度汇报 ──
  20. 向用户输出本章完成状态与进度看板
  21. 检查停止条件（用户要求停 / 达到指定章数）→ 满足则输出结算看板并停止
  22. 更新 auto_state.json，继续下一章

全部章节完成后：
  23. 汇总 session_log 中全部 🟡/降级🔴 条目，输出《待处理建议清单》（自动模式不自动修复🟡）
  24. 执行 /finish（按序合并所有 {project_dir}/drafts/chXX.md 为完整小说文件）
  25. 自动触发两轮全稿审阅（分块协议见上方"两轮全稿审阅协议"）
  26. 全稿审阅中 [采纳]+🔴 的问题自动派发 Writer 修复（同样有界：最多2轮，失败降级🟡）
  27. 向用户输出最终完成报告（含《待处理建议清单》与批量处理提示）
```

### 运行期干预（上帝指令与暂停）

自动写作运行期间，用户随时可以直接输入自然语言消息（无需等待暂停）。Director 在**每个章间检查点**处理未消费的用户消息：

```
1. 内容类指令（如"第5章前让角色X正式出场"、"节奏太慢，压缩支线"）：
   - 与 truth.md / relationship_arc.md 不冲突 → 写入 {project_dir}/meta/directives.md，
     在后续 Writer prompt 的"上帝指令"节注入
   - 与真相冲突（如指定了与真相不符的凶手）→ 标记为 blocked，
     在本章进度看板中提示用户；致命冲突则暂停等待用户确认
2. 停止类指令（"/auto-pause"、"停下来"、"先停一下"）：
   → 当前章节流水线完整走完后停止，输出结算看板与恢复方式
3. 范围类指令（"写到第8章停"）：
   → 更新停止条件，写入 auto_state.json
4. 所有已处理的指令在 directives.md 中标记状态（done / blocked / pending）
```

`/auto-pause [项目名]` 为显式暂停指令：若自动流水线正在运行，等效于上述停止类指令；若已停止，仅输出当前状态与恢复方式（`/auto-write` 从断点续写）。

### 异常处理

| 异常场景 | 处理机制 |
|----------|----------|
| Writer 返回 <prose> 缺失/截断 | 重试整个 Writer 子任务 1 次；仍失败 → 暂停并向用户报错请求干预 |
| Writer 未写入/未增长 draft 文件 | <prose> 完整则 Director 代为写入；否则按上一条处理 |
| 字数低于硬约束下限 | 派发补写子任务（仅补写，不重写）；仍不足则接受并记录 |
| 关键 XML 标签缺失/不可解析 | 轻量重试（仅重发缺失标签部分）1 次；Chooser 仍失败默认选 A；Reviewer 仍失败跳过本章审阅标记 ⚠️ |
| 选项公平性可疑 | 要求 Writer 仅重发 <choices>，并附选项公平性原则提醒 |

| Reviewer 子任务失败 | 重试 1 次；仍失败 → 本章跳过审阅，标记 ⚠️，不阻断主流程 |
| 修复循环 2 轮未成功 | 降级为 🟡 记录到 session_log，继续推进 |
| 草稿写入冲突或状态不一致 | Director 重新扫描 `{project_dir}/drafts/` 读取最新实体文件 + auto_state.json 后重新组装 prompt |
| 上下文过长 | 章间蒸馏（见 auto_agents.md 6.8）：session_log 压缩、clues 归档、characters 状态快照化 |

## `/auto-chapter [项目名|new]` — 单章自动写作

与 `/auto-write` 采用相同的 Director / Writer / Chooser / Reviewer 四角色协作机制（含输出核验、有界修复循环、auto_state.json 检查点），但执行范围仅限定为**当前正在进行的这一个章节**。

### 执行流程

1. 执行 `/auto-write` 相同的前置检查与项目锁定（含中断恢复；若为 `new` 则先初始化并自动写完第1章）
2. 仅执行当前单章的写作流水线（第1段 → Chooser → 第2段 → Chooser → 第3段收拢 + 章节封存 → Reviewer 审阅 → 过滤 → 🔴有界自动修复）
3. 章节完成后更新 auto_state.json，输出本章结算看板与决策提示：

```
✅ 第 {N} 章 自动写作完成 ({字数}字)

Chooser 选择路径：{段1选择} → {段2选择} → 收拢
审阅结果：{🔴×0 🟡×1 🟢×2}（🔴 已自动修复 {n} 处；降级 {m} 处）

下一步可选：
- 输入 /auto-chapter 继续自动写下一章
- 输入 /auto-write 自动写完剩余全部章节
- 输入 /write 切回交互式单段手动共创
- 输入 /plan 先讨论后续章节架构
- 说"批量处理🟡" 逐条修复本章记录的建议问题
```

## `/auto-pause [项目名]` — 暂停自动写作

**适用场景**：自动写作流水线运行中或已停止时，请求暂停 / 查看恢复方式

### 执行逻辑

```
1. 确认目标项目 {project_dir}
2. 若自动流水线正在运行：注册停止条件——当前章节流水线完整走完后停止
   （不中断本章，保证章节完整性：写完当前段落的收拢、封存、审阅、修复）
3. 若已停止：输出当前断点状态与恢复方式
4. 停止时输出结算看板：
   - 已完成章节列表与审阅统计
   - 断点位置（第 X 章第 X 段 / 章间）
   - 未消费的上帝指令（若有）
   - 恢复方式："输入 /auto-write {项目名} 从断点续写"
```
