# 全自动小说写作：上下文与 Token 优化设计

日期：2026-09-06  
状态：工程实施建议，尚未修改 Skill 或运行成本对照实验  
范围：`skill-src/` 的全自动写作流程；交互式写作保持原有交互语义

## 1. 目标与结论

用户反馈：写完一部小说约使用 500K 上下文或 token，并耗尽 Antigravity 一个 5 小时额度窗口。该 500K 尚未确认是累计消耗还是单会话占用，不能作为精确成本归因依据。

源码分析表明，主要开销来自：

1. 自动模式沿用交互模式的三段写作与两次选路，每章至少调用 6 次子任务。
2. 正文写入文件后全文返回 Director，再由 Director 内联给 Reviewer。
3. 同一状态和规范在多个 Writer 任务中重复读取、解释。
4. 模型承担文件核验、状态更新、摘要维护、合稿等大量机械工作。
5. 检查职责重叠，修复只有单问题上限，没有章节或全书预算。
6. 磁盘上的 meta 蒸馏没有解决主会话历史累积。

推荐实施顺序：**整章生成 → 正文不回流 Director → 确定性维护脚本化 → 章间会话恢复 → 按实测调整审阅频率。**

第一阶段保留每章独立 Reviewer，避免同时改变生成粒度和审阅覆盖率，导致质量变化无法归因。不承诺固定 token 降幅或平台额度节省比例。

### 2.1 已有优化应保留

当前已有题材按需加载、核心设定骨架、投放物索引、近期摘要、工具定向核验、轻量重试、短进度报告。这些方向正确，应统一语义并继续使用，而不是全部推翻。

### 2.2 必须保留的保障

- 目标项目隔离与明确写权。
- 核心事实、角色知识边界、关键结构约束。
- Reviewer 的独立读者视角，不能由已经看过终局设定的 Writer 自称切换视角替代。
- 文件落盘、版本与提交状态核验。
- 修复正文后同步更新受影响状态。
- 关键节点检查和异常恢复。

一般文学偏好不应直接触发强制修复。例如密度偏高、修辞偏多，可以报告为建议；只有违反明确项目约束或实质损害理解时才提升严重级别。

## 3. 成本模型与测量边界

必须分别记录：

- 单次请求或会话的上下文峰值。
- 全次运行累计输入与输出 token。
- 平台可提供的缓存 token、推理 token 及计费信息。
- 子任务数、实际模型请求数、工具调用数。
- 用时、重试数、修复轮数与正文长度。

子任务不等于一次模型请求；读取文件可能引发多轮请求。路径代替内联只能避免不必要搬运，子任务读入的正文依然占用其上下文。

按当前流程，12 章基础调用为 72 次子任务。整章 Writer 加每章 Reviewer 后为 24 次，基础子任务数减少约 67%；**这不是总 token 节省率**，尚未计入初始化、Solver、维护、修复和最终审阅。

12 章若按 1–4、4–7、7–10、10–12 分块，每轮读取 15 章份正文，两轮为 30 章份，即约 2.5 遍全书正文。分块降低单次峰值，不代表降低累计 token。

当前源码配置了 Writer、Reviewer 的高思考档，以及特殊 Writer 的最高档。不能仅凭配置文件推断供应商实际执行或收费方式；应根据实际请求及 usage 验证。初轮对照实验保持模型和思考档位一致。

## 4. 目标流程

```text
加载检查点，确定本章与基础状态版本
    ↓
构建作者资料包、读者资料包
    ↓
Writer 一次生成整章 + chapter_delta
    ↓
脚本执行确定性检查
    ↓
Reviewer 独立审阅正文与读者资料包
    ↓
需要时批量修复，重新核对受影响状态
    ↓
提交章节和状态，保存检查点
    ↓
命中关键节点时执行 Solver；继续下一章
```

### 4.1 模式划分

- `/write`：保留单段推进、真实用户选择及暂停行为。
- `/auto-write`、`/auto-chapter`：默认整章生成，不生成三选项，不调用 Chooser。
- 如需模拟读者选路，提供显式可选策略；不要默认承担该成本。
- 整章输出若遭平台截断，应从已确认的章节版本继续，不自动重写全章，也不依赖字数猜测完成状态。

### 4.2 Writer 的最小资料包

每章提供：

1. 项目目录、题材、语言、章号、基础状态版本。
2. 本章目标、必须发生的变化、章末目标状态。
3. 核心设定骨架和本章相关依据。
4. 出场人物的章初位置、身体和物品状态、已知信息、称谓及声音示例。
5. 本章相关投放物全文与简短全局索引；触及其他条目时按需读取。
6. 最近章节摘要与上一章末尾原文。
7. 本章相关历史事实、场景复访记录和未解决约束。
8. 精简的文风规则及题材写作钩子。

资料包不能完全取代原始正文。相关性选择遗漏、隐含关系、语气或前文回声需要原文支持时，允许定向回读，并记录补充读取的原因和体积。

初始预算按资料包类别设置可配置上限；超限先缩短不相关内容或拆分加载，禁止无条件截断关键事实。具体 token 上限以对照实验确定，不从字符数直接宣称精确 token 数。

### 4.3 Writer 返回契约

自动模式不返回全文。建议提供等价的结构化结果：

```json
{
  "chapter": 4,
  "base_revision": "state-003",
  "draft_path": "drafts/ch04.pending.md",
  "delta_path": "meta/pending/ch04.delta.json",
  "reader_summary": "仅包含正文已经公开的信息",
  "author_notes": "仅报告偏差和待核查问题",
  "status": "ready_for_review"
}
```

路径、长度、哈希和文件是否存在由脚本实际核验，不能盲信模型自报。`author_notes` 不得进入读者资料包。原有 XML 可继续用于迁移阶段；关键是契约唯一、字段明确，而非必须换成 JSON。

### 4.4 Reviewer 与 Solver

- 第一阶段每章保留独立 Reviewer。
- Reviewer 自读章节文件与已生成的读者资料包；不得读取作者资料包、未公开计划或终局设定。
- 读者资料包优先采用公开字段白名单生成；自由文本摘要仍可能泄露，需要定义可见性来源，不能认为删掉几个字段就足够。
- 报告只包含有证据的问题、位置、影响和建议；无问题给简短结果，不逐维度输出通过说明。
- Solver 仅在题材定义的关键节点触发，并按节点和章节版本去重。
- 若关键节点同时需要 Reviewer 和 Solver，明确两者分工，避免同一输入下重复回答相同问题。
- 后续是否减少 Reviewer 频率，单独实验验证，不纳入首轮默认改动。

## 5. 状态与工具职责

### 5.1 保存历史，限制工作集

分离三个概念：

- **原始历史**：正文版本、事实成立记录、信息获得事件、修改记录，不因 prompt 预算而丢弃。
- **当前快照**：角色状态、活动投放物、未解决约束。
- **本章工作资料包**：从前两者选择出的必要子集，可重新生成。

不再以“历史文件超过 150 行”作为启动 LLM 蒸馏的充分条件。历史大但工作集小，不需要维护模型介入。

### 5.2 chapter_delta 最小结构

```text
chapter / base_revision
new_facts / revised_facts
scene_changes
character_state_changes
information_acquisitions
signal_changes
outline_deviations
unresolved_issues
source_passages
```

事实与信息获得事件应包含来源位置；信息获得应包含获得者、获得内容、来源及章内顺序。知识边界核查基于章初状态加顺序事件，不能仅使用章末快照。

LLM 负责提取语义变化，脚本负责结构、引用、版本和提交；脚本不能凭结构合法证明小说语义一致。正文新事实遗漏于 delta 是需要专门验证的风险。

### 5.3 脚本适合承担的工作

- 按统一规则统计中文字符、英文词数，排除标题等非正文区域。
- 检查路径、章节状态、基础版本、文件哈希与必要字段。
- 检查引用编号是否存在、提交是否重复。
- 生成有界资料包、维护索引与当前快照。
- 追加结构化运行记录，输出短结果，避免回显全文。
- 根据已提交章节清单排序合稿；最终修复后重新合稿。

题材语义、编号模式、触发规则等通过题材包配置提供；共享脚本不硬编码具体题材行为。

### 5.4 提交与恢复

多文件写入不能假装天然原子化。建议采用提交记录与版本号，使“部分完成”可识别、可恢复：

1. Writer 写待审正文和 delta，不先修改权威状态。
2. 检查和审阅针对同一正文版本。
3. 修复后重新生成受影响 delta，失效的审阅结果不能视为覆盖新版本。
4. 提交前校验 `base_revision`，不匹配则重新对齐。
5. 提交记录列出正文、状态和摘要版本；中断后恢复未完成提交。
6. 正文和权威状态提交完毕才标记章节完成。

不得因正式章节文件存在就认定封存、审阅、修复均完成。不得未经确认删除旧文件；需要清理残留时遵守工作区删除政策，优先让恢复逻辑识别并忽略非权威版本。

旧项目迁移只执行一次：检查索引与必要字段，生成可恢复检查点，保留旧记录；避免每章因旧格式缺字段退回全文读取。

## 6. 审查与修复预算

建议区分：

- **阻断问题**：文件损坏、状态版本冲突、明确核心事实矛盾、关键内容缺失。
- **必须修复的正文问题**：有证据的知识越界、逻辑断裂、违反明确项目硬约束。
- **建议问题**：修辞密度、局部节奏、可选风格改善。

同章必须修复项合并为一次任务，复核后最多追加一轮；复核主要针对改动区域和依赖事实。增加全书总修复预算与明确耗尽策略。

一般文学建议可以记录后继续。硬性正确性问题预算耗尽时，不得静默标为通过：保留未通过状态并报告，必要时暂停。原有“所有红色问题最终降黄继续”需要按问题性质细分。

字数使用章级可配置目标及容差；不要为轻微偏差启动补写。追加、替换、续写必须指定目标版本，消除“重新 append”歧义。

## 7. 会话与全稿审阅

### 7.1 Director 保持短上下文

Director 保留运行策略、检查点、当前章短报告和未解决问题，不接收每章完整正文或重复内联大型资料。

磁盘摘要变短不会自动删去会话历史。需核实宿主支持的压缩或新会话机制，在章间按预算轮换。恢复包包含：项目路径、协议版本、已提交状态版本、当前步骤、待修复事项、未消费用户指令和下一章任务。

不能依赖提示词“忘掉前文”实现上下文释放，也不能在未验证宿主能力前声称已经支持自动轮换。若宿主不提供自动轮换，提供明确的恢复入口并报告该限制。

### 7.2 全稿审阅唯一入口

全稿审阅只由一个步骤调度，记录对应全书章节版本集合：

1. 一致性审阅先利用全书事件、事实和人物状态历史，定位风险后回读原文。
2. 文学审阅保留正文阅读需求，按预算分块；跨块使用短摘要及必要原文，不默认重复整章。
3. 全书级事实索引负责支持远距离关系定位；块间重叠不能替代它。
4. 报告去重后批量修复；对修改区域及相关跨章依赖复核。
5. 最后重新合稿，并验证合稿使用所有最新已提交章节。

减少原文覆盖可能漏掉未登记事实和细微文学问题，因此全稿审阅改造放在基础流程优化验证之后实施。

## 8. 分阶段实施与文件分工

| 阶段 | 工作 | 完成标准 |
|---|---|---|
| P0：明确基线和契约 | usage 记录；消除读取、写权、审阅入口冲突；修正补写歧义 | 每个步骤有唯一输入输出和执行时机；可观察实际成本 |
| P1：精简自动流程 | 整章 Writer、默认关闭 Chooser、短报告、Reviewer 自读；保留每章审阅 | 正常章节只有一次 Writer 和一次 Reviewer 主任务；Director 不接收全文 |
| P2：状态与工具 | 资料包生成、delta、版本化提交、精确长度统计、脚本合稿、旧项目迁移 | 可恢复、可幂等重跑；修复后的正文与状态一致 |
| P3：会话与审阅优化 | 宿主会话恢复、Solver 去重、修复总预算、全稿定向审阅 | 有实测上下文上限与质量对照，不能只证明调用数下降 |

文件建议：

- `skill-src/SKILL.md`：保留入口、模式选择和生命周期路由；自动模式不必全文加载交互指令手册。
- `references/auto_agents.md`：自动流程和角色契约的单一权威来源；可按角色拆分为按需加载文件。
- `references/writing_loop.md`：保留交互语义；引用自动流程，避免复制完整编排。
- `references/genres/{genre}/`：题材阈值、专项检查、关键节点、相关模板和字段。
- `scripts/`：确定性维护与测量，必要时新增小型运行辅助程序。
- `platform/opencode/agents/`：与新角色契约同步；平台专属能力在平台适配层定义。

不要求首轮一次性引入数据库或完整状态引擎。可以先以 Markdown 加结构化旁文件验证流程，再决定长期存储方案。

## 9. 验收与对照实验

### 9.1 功能验收

- 自动模式默认不生成选项，不派发 Chooser；交互模式继续等待真实用户选择。
- Writer 不回传正文全文；Director 不为核验或转交而读取全文。
- 资料包中每个关键约束可追溯；读者资料包无未公开设定。
- 断点可区分生成、审阅、修复、提交阶段，不猜段数，不重复正文。
- 同一章节提交重复执行不会重复追加状态或修改记录。
- 用一条“角色在章中才知道某事实”的样例验证章初知识越界能被识别。
- 修改章节后，受影响状态与最终合稿更新到一致版本。
- 超预算有明确行为和记录；不能把失败标成成功。

### 9.2 成本与质量对照

用同一大纲、相同模型配置、相近正文长度比较：

1. 当前流程。
2. 整章 Writer + 每章 Reviewer + 短报告。
3. 在方案 2 上增加资料包和状态工具。

至少覆盖普通章、结构转折章、收束章。若条件允许，进行多次生成，避免把随机质量差异当作架构效果。

记录每千正文字符或词的输入、输出及可获得的推理 token；单独记录峰值上下文、实际模型请求数、子任务数、工具调用数、耗时与修复数。缓存命中与未命中分开统计，平台未提供的指标标记未知，不估装成实测。

人工或独立盲评比较：事实矛盾、角色知识越界、投放遗漏、无功能场景重复、人物声音、节奏和整体可读性。条件允许时给历史事实、知识边界和场景复访准备固定检查样例。

验收不能仅看 token 下降：应在约定的质量容差内降低成本。具体节省目标在基线测量后确定。
