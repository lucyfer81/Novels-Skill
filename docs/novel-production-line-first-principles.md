# 悬疑小说生产线：第一性原理分析与路线选择

> 本文讨论的问题：对于需要长期保持人物、时间线、线索和场景连续性的悬疑长篇，使用 Skill、多 Agent 流水线或 Python pipeline 是否合适，以及如何在可读性、速度和成本之间取得更好的平衡。
>
> 分析原则：暂时忽略行业惯例、现有实现和“通常应该这样做”的理由，只从基本事实、真正目标和真实约束出发重新设计。

## 一、结论摘要

Skill 适合承载写作工艺、题材知识、写作人格、审阅标准和人机交互协议；它不适合独自承担长篇小说的权威状态存储、事务提交和高频执行调度。

当前 Skill 的质量相对均衡，主要是因为它用重复读取、多角色隔离、章节审阅和状态登记，弥补了语言模型没有可靠长期记忆的问题。这种方法有效，但把大量成本花在了重复理解同一批信息上。

Python pipeline 反复出现前后逻辑不一致和场景无故重复，并不说明 Python 不适合写小说。更可能的根因是：把正文、摘要或一组 Markdown 文件当作“记忆”，却没有建立权威的、可提交、可验证的故事状态。

建议采用混合架构：

```text
Skill       负责写作工艺、题材规则、人格和评审标准
Python      负责权威状态、上下文编译、确定性检查、检查点和成本统计
LLM         负责结构创作、正文生成和少量语义判断
```

如果只做一项优先改动，应当删除自动模式中的高频 Chooser，让 Writer 输出“正文 + 最小状态差异”，并只在结构风险节点调用专项审阅。

## 二、基本事实

### 1. 模型调用之间没有天然的故事记忆

模型写第八章时，真正能使用的只有本次输入中的信息。此前写过、但没有出现在当前上下文里的事实，对模型而言等于不存在。

因此，“模型以前写过这个场景”不等于“模型现在知道自己写过这个场景”。

### 2. 提供上下文不等于模型会正确使用上下文

上下文不是数据库查询。事实即使出现在很长的输入中，也可能因为距离当前任务太远、被规则淹没、表达方式不显著，或与模型更强的常见模式冲突，而被忽略。

所以需要解决的不是单纯的“有没有把前文塞进去”，而是：

- 当前任务真正相关的事实是什么；
- 哪些事实必须以最高优先级出现；
- 哪些事实已经失效；
- 模型是否理解这些事实的来源和状态。

### 3. 小说正文是低效且含混的状态存储格式

一句“她又把手放到门把上”，可能同时包含地点、门的状态、人物的犹豫、场景复访和意象重复等信息。这些状态埋在散文中，既不容易被 Python 精确提取，也不容易被模型每次稳定复原。

正文适合给读者阅读，不适合直接充当数据库。

### 4. 每一章既消费状态，也创造状态

正文会不断产生计划外事实，例如新道具、新称谓、人物临时经历、谁看见了什么、物品位置变化和新的关系变化。

如果这些新增事实没有在章末被提交到状态系统，下一章就会丢失。长篇写作的真实循环不是：

```text
读取前文 → 写下一章
```

而是：

```text
读取当前状态 → 写作 → 提取新增状态 → 检查冲突 → 提交状态
```

### 5. 创作和约束满足是不同的认知任务

写出有感染力的正文，需要开放联想、语言节奏和适度随机性。检查时间线、知识边界、证据来源和称谓，需要低随机性和逐项核对。

把两者塞进同一次生成，模型通常会牺牲其中一部分。当前 Skill 将任务拆成 Writer、Reviewer、Solver、Director，方向上是对的，但拆分频率过高，导致成本显著增加。

### 6. 场景重复不是地点重复

同一个地点可以合理出现多次。真正需要防止的是：

```text
地点相似
+ 场景功能相同
+ 人物进入状态相同
+ 描写素材相同
+ 没有新的结果
```

仅记录“第 3 章写过医院”无法解决这个问题。需要记录场景目的、进入状态、关键变化和退出状态。

### 7. 当前 Skill 的稳定性来自冗余，而非每一环都不可替代

当前流程会重复读取核心设定、角色、线索、最近章节和连续性登记，再经过 Reviewer 与 Director 过滤。这相当于使用多次语义计算换取可靠性。

这证明“状态提醒和审查能改善一致性”，但没有证明“每章三次 Writer、两次 Chooser、一次 Reviewer 都是必要的”。

### 8. 正文生成是不可消除的基本成本

要写三万字小说，至少要生成三万字正文，这是成本下限。但反复让多个模型重新理解同一份 truth、角色表和线索表，不是不可消除的成本。

理想系统中，每章输入量主要取决于本章涉及的活动事实，而不是取决于全书已经写了多长。

## 三、未验证假设

### 关于 Skill 的假设

- 必须由 Agent 自己阅读多个 Markdown 文件，才能保持一致性。
- 每一段都必须重新注入核心设定。
- 每章都必须经过独立 Reviewer。
- 多 Agent 一定比单 Agent 加可靠状态更好。
- 更高 reasoning 档位一定能提高文学质量。
- 一章分成三段一定更容易控制。
- 自动模式也必须在每段之间执行三选一。
- 模型生成的章节摘要足以代表该章。
- 模型报告“meta 已更新”，就意味着状态确实正确。
- 规则越详细，模型越不容易犯错。

最后一条尤其危险：规则太多时，模型可能更擅长输出合规报告，但正文变得机械。

### 关于 Python pipeline 的假设

- Python 无法处理语义一致性。
- Python 必须把全部前文交给模型。
- 只要摘要足够完整，就能替代前文。
- 场景重复只能依靠模型自行发现。
- 一致性问题必须在正文生成后，用另一次完整审阅解决。
- 结构化状态会限制文学创造力。
- 每个新增事实都必须在正文前提前规划。
- 一章生成失败只能整章重写。

这些都不是 Python 的固有限制，而是当前状态表示和执行协议的设计选择。

### 关于问题根因的假设

还需要验证一个容易被忽略的假设：

> 细节矛盾只是因为模型忘记了前文。

实际原因也可能是大纲自身冲突、章末状态提取错误、上下文包含两个版本、事实优先级不够高，或者模型为了完成当前戏剧目标而主动牺牲一致性。

如果不区分这些原因，单纯增加上下文只会越来越贵。

## 四、真正目标

真正目标不是“使用 Skill 写小说”，也不是“让 Python pipeline 正常工作”。目标是：

> 在可接受的成本和等待时间内，持续生成可读的悬疑长篇；全书事实、时间、人物知识和线索推导保持一致；场景重复必须带来新的信息、关系或状态变化；最终文本可以局部修复，而不必频繁整章重写。

这个目标包括五层结果。

### 硬约束

- 人物不能在错误时间出现。
- 人物不能使用自己尚未获知的信息。
- 物品位置不能无解释地改变。
- 侦探不能引用未投放证据。
- 已被推翻的事实不能无理由复活。
- 同一事件不能出现不兼容版本。

### 软约束

- 人物声音稳定。
- 文风稳定。
- 节奏有张弛。
- 场景有新鲜感。
- 悬念持续有效。
- 情绪和主题能够累积。

### 创作目标

- 人物有主动欲望，而不是只负责搬运线索。
- 场景具有目标、阻力、转折和结果。
- 线索隐藏自然且回看成立。
- 推理过程公平。
- 反转既意外又可追溯。

### 运行目标

- 可以断点恢复。
- 可以局部重写。
- 状态变化有来源。
- 能解释为什么某章被修改。
- 失败不会污染后续章节。

### 经济目标

- 普通章节尽量只进行一次高质量正文生成。
- 高成本审查集中在结构风险节点。
- 随着历史增长，每章成本不要近似线性增长。
- 低价值的格式整理、索引和确定性检查不交给昂贵模型。

## 五、真实约束

### 确实存在的约束

- 模型没有可靠的跨调用长期记忆。
- 模型对很长上下文的利用率有限。
- 小说正文会不断创造计划外事实。
- 一致性问题有一部分必须进行语义判断，纯规则无法全部解决。
- 悬疑小说必须提前固定相当一部分终局事实和证据关系。
- 章节之间存在串行依赖，不能完全并行生成。
- 每次模型输出都有违反约束的概率。
- 成本随输入、输出、推理量和调用次数增加。

### 不是真实约束的东西

- 每章必须三段。
- 每段必须 850–950 字。
- 必须有 Chooser。
- 必须每章运行 Reviewer。
- 必须使用 Markdown 保存状态。
- 必须由 Writer 更新全部 meta。
- 必须每次读取完整角色表或线索表。
- 必须把 Skill 和 Python 二选一。
- 必须在一次生成中同时完成正文、审查和状态维护。
- 同一个地点不能重复出现。
- 所有文学问题必须边写边修。

## 六、从零设计的四条路线

### 路线一：精简版单 Agent Skill

#### 核心机制

保留当前 Skill 作为运行环境，但将热路径缩减为：

1. Director 生成本章契约；
2. Writer 一次生成整章；
3. Writer 输出正文和最小状态差异；
4. Director 做确定性核验；
5. 仅在命中高风险条件时调用 Reviewer 或 Solver。

本章契约只包含：本章目标、人物状态、活动线索、不可违反的事实、已使用场景签名以及本章必须产生的变化。

#### 最大优势

改造最小，可以快速验证减少调用后质量是否仍然稳定。现有悬疑工艺和题材包基本可以保留。

#### 最大风险

核心状态仍然主要存放在自然语言 Markdown 中。Agent 可能漏读、误读，或者在提交状态差异时遗漏新事实。

#### 最需要验证的假设

一份压缩后的章节契约，是否足以替代大量重复读取和多角色审查。

### 路线二：Python 状态引擎 + Skill 写作宪法

#### 核心机制

Python 不负责教模型怎么写，只负责：

1. 保存权威状态；
2. 为本章编译最小上下文；
3. 检查生成结果；
4. 原子化提交状态。

Skill 保留悬疑工艺、文风要求、线索公平性、人格和评审标准。

状态记录应包含事实内容、首次成立章节、当前状态、来源段落、可见人物、是否允许推翻及推翻依据。场景记录应包含地点、时间、参与人物、场景目的、进入状态、核心冲突、新增信息、关系变化、退出状态和已使用感官意象。

每章执行一次状态事务：

```text
编译章节契约
    ↓
生成正文 + state_delta
    ↓
规则检查
    ↓
必要时进行一次语义检查
    ↓
通过：正文和状态一起提交
失败：局部修复或拒绝提交
```

场景重复不应被简单禁止，而应检查：历史场景与当前场景高度相似时，是否有新增事实、关系变化、物理状态变化，或明确声明为有意回环。

#### 最大优势

把昂贵的模型注意力集中到真正需要语义和创作的地方。状态选择、引用追踪、时间检查、线索编号和场景相似度筛查交给 Python。

成本可以从“每章多次重读全局状态”变成“每章一次正文生成，按风险触发审查”。

#### 最大风险

状态模式过细，会把小说变成数据库驱动的组装文本；状态过粗，又无法解决一致性问题。另一个风险是 state_delta 不完整，正文悄悄创造新事实却没有进入状态库。

#### 最需要验证的假设

影响后续一致性的事实，能否可靠地提取为有界、结构化的状态差异。

### 路线三：先完成全书事件模拟，再渲染正文

#### 核心机制

第一阶段不写正文，只构建并验证全书事件时间线、角色位置和知识状态、场景目的和结果、线索投放与推翻关系、章节信息增量以及场景复访理由。

这一阶段相当于运行一个没有文采的故事模拟器。逻辑通过后，第二阶段将场景卡渲染成正文。正文不得改变核心事件，只能添加不影响逻辑的表现性细节；新产生的重要事实需返回规划层审批。

#### 最大优势

悬疑逻辑最容易控制。时间线、知识边界和线索公平性在正文生成前就能发现，正文可以按章甚至按幕批量生成。

#### 最大风险

人物可能像在执行事件清单，作品缺乏自然生长和意外感。规划过严会使文字“正确但不活”。

#### 最需要验证的假设

一部好看的悬疑小说，其主要创造价值是否可以在事件和信息结构阶段提前完成。

### 路线四：长上下文分幕写作 + 幕间对账

#### 核心机制

以幕为单位持续写作，而不是每一段启动独立任务。每幕内部保留完整上下文，幕间进行一次状态对账和局部修复。

#### 最大优势

调用次数少，人物声音和叙事流动性可能最好。模型不需要每 900 字重新启动和重新理解角色。

#### 最大风险

一幕内部的早期错误会传播到后续章节，修复范围可能较大。长上下文也不保证精确记忆。

#### 最需要验证的假设

当前模型是否能在一次长上下文写作中稳定维持一个幕的事实和场景记忆。

## 七、推荐架构

推荐路线二，并用路线一作为迁移步骤。

```text
Skill
  └─ 题材工艺、写作人格、评审标准、人机命令

Python 状态引擎
  └─ 权威事实、场景记忆、上下文编译、验证、提交、成本统计

Writer
  └─ 每章一次正文生成 + state_delta

风险触发器
  └─ 只在假设推翻、揭示、终局、冲突或节奏异常时调用专项审阅
```

关键不是让模型反复阅读整个项目来“回忆小说”，而是由系统明确告诉它：

- 本章必须知道什么；
- 本章不能违反什么；
- 本章必须改变什么；
- 本章结束时必须提交什么状态。

当前 Skill 可以保留为“创作宪法”，但不应继续同时充当数据库、事务系统和高频调度器。

## 九、关键验证实验

在重构前，建议先做一个小型对照实验，而不是一次性改造整条生产线。

取一部已有小说的连续 6 章，准备一组人工标注的测试项：

- 10 条事实；
- 5 条人物知识边界；
- 3 个物品位置变化；
- 3 个场景复访；
- 3 条线索投放关系；
- 2 个必须保持的称谓或说话习惯。

比较三种输入方式：

1. 只给最近章节；
2. 使用当前 Skill 的完整流程；
3. 使用“结构化状态 + 最近一章原文 + 本章契约”。

至少记录：

- 事实冲突数；
- 人物知识越界数；
- 无功能场景重复数；
- 线索引用错误数；
- 正文可读性人工评分；
- 总输入 token；
- 总输出 token；
- 调用次数；
- 生成和修复总时间。

最有价值的不是绝对分数，而是观察第三种方式能否在显著降低输入和调用的同时，保持与当前 Skill 接近的连续性质量。

## 十、最关键的方案分叉假设

最可能彻底改变方案的假设是：

> 影响后续一致性的叙事状态，可以从正文中可靠提取，并压缩成有限的结构化状态；后续模型只读取这份状态和少量原文，仍能写出自然、连贯的小说。

如果这个假设成立，Python 状态引擎路线成立，Skill 中高频读档和多 Agent 冗余可以大量删除。

如果这个假设不成立，例如关键连续性大量依赖无法结构化的语气、隐含关系、细微动作和原文回声，那么系统就必须保留更多原始正文，转向分幕长上下文或高成本 Agent 重读，成本不会像预期那样下降。

因此，下一步最重要的不是继续增加规则，而是验证“有限状态是否足以承载长篇连续性”。
